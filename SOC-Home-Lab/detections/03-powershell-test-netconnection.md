# Detection 03: PowerShell Test-NetConnection Custom Rule

## Purpose

Detect PowerShell process creation where the command line contains `Test-NetConnection` so that an analyst can review the command, process context, destination being tested, and related Sysmon network telemetry.

This scenario was used to practise basic detection engineering by creating and validating a custom Wazuh rule rather than relying only on a built-in alert.

## Threat / Behaviour

`Test-NetConnection` is a legitimate Windows PowerShell command used for connectivity and port testing. Its presence is not automatically malicious.

In a real environment, similar activity may deserve review when it is unexpected, repeated across many destinations or ports, launched from an unusual parent process, or associated with other suspicious behaviour.

## Data Sources

- Sysmon Event ID 1 - Process Create
- Sysmon Event ID 3 - Network Connection
- Wazuh

## Detection Logic

The custom Wazuh rule was added to:

`/var/ossec/etc/rules/local_rules.xml`

The rule used in the lab was:

```xml
<group name="windows,sysmon,custom,">

  <rule id="100100" level="6">
    <if_group>sysmon_event1</if_group>
    <field name="win.eventdata.commandLine" type="pcre2">(?i)Test-NetConnection</field>
    <description>Custom detection: PowerShell Test-NetConnection executed</description>
    <group>custom_detection,powershell,network_activity,</group>
  </rule>

</group>
```

The configuration was syntax-tested before the Wazuh manager was restarted.

## Trigger Conditions

The rule fires when:

1. Wazuh receives a Sysmon Event ID 1 process-creation event.
2. The event belongs to the `sysmon_event1` group.
3. The process command line contains `Test-NetConnection` using a case-insensitive PCRE2 match.

## Validation

The detection was safely tested on the monitored Windows endpoint by deliberately launching a new PowerShell process:

```powershell
powershell.exe -NoProfile -Command "Test-NetConnection 192.168.56.101 -Port 443"
```

The test targeted the lab Wazuh manager at `192.168.56.101` on TCP port `443`.

Wazuh generated:

- **Rule ID:** `100100`
- **Rule level:** `6`
- **Rule description:** `Custom detection: PowerShell Test-NetConnection executed`
- **Agent:** `Windows-Host`

## Observed Evidence

- **Host:** `Windows-Host` / `LAPTOP-C7OPSS6H`
- **Endpoint IP:** `192.168.56.1`
- **Process:** `C:\\Windows\\System32\\WindowsPowerShell\\v1.0\\powershell.exe`
- **Command line:** `powershell.exe -NoProfile -Command "Test-NetConnection 192.168.56.101 -Port 443"`
- **User:** `LAPTOP-C7OPSS6H\\hasna`
- **Process ID:** `15676`
- **Parent process:** `powershell.exe`
- **Parent PID:** `12640`
- **Integrity level:** `High`
- **Destination IP:** `192.168.56.101`
- **Destination port:** `443`
- **Protocol:** `TCP`
- **Wazuh rule ID:** `100100`
- **Wazuh level:** `6`

## Correlation

Sysmon Event ID 3 was reviewed locally on the Windows endpoint for PID `15676`.

The event showed that the same PowerShell process initiated a TCP connection:

- **Source IP:** `192.168.56.1`
- **Source port:** `58463`
- **Destination IP:** `192.168.56.101`
- **Destination port:** `443`
- **Initiated:** `true`

This correlated the process-creation alert with the actual network connection generated by the test command.

## MITRE ATT&CK Mapping

- **Tactic:** Execution
- **Technique:** PowerShell
- **Technique ID:** T1059.001

This mapping is supported because the telemetry directly shows PowerShell execution.

No network-scanning or command-and-control technique was assigned. A single controlled connection to one lab destination and one port does not provide enough evidence to claim scanning or C2 activity.

## False / Benign Positives

Legitimate causes can include:

- Administrator connectivity testing
- Troubleshooting
- Help-desk diagnostics
- Automation scripts
- Monitoring or deployment scripts
- Controlled security testing

## Triage Steps

1. Validate the Sysmon Event ID 1 process-creation event.
2. Review the executable image and full command line.
3. Identify the user, PID, parent process, parent PID, integrity level, and time.
4. Determine the destination IP and port referenced by the command.
5. Correlate the process with Sysmon Event ID 3 network telemetry where available.
6. Scope for additional network connections from the same PID.
7. Scope for child processes launched by the detected process.
8. Compare the activity with expected administrative or user behaviour.
9. Classify and escalate only when supported by the evidence.

## Result

- **Classification:** Benign Positive
- **Wazuh alert level:** 6
- **Investigation severity:** Low
- **Escalation required:** No

The alert was technically correct, but the command and network connection were deliberately generated in the controlled lab.

## Lessons Learned

A useful custom detection should turn specific telemetry into an actionable alert without assuming the activity is malicious.

This scenario also demonstrated process-to-network correlation: Sysmon Event ID 1 showed the process and command line, while Sysmon Event ID 3 showed the network connection generated by that exact process ID.
